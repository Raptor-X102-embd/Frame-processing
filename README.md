# FPGA Image Processing — учебный проект

Учебный проект по обработке изображений на SystemVerilog с прицелом на реализацию в FPGA. Цель — шаг за шагом разобраться в конвейерной обработке видеопотока, работе с фиксированной точкой, интерфейсах ввода/вывода данных (SPI, VGA) и в итоге собрать полноценный pipeline на реальной плате.

Сейчас реализован полностью рабочий сквозной путь:
изображение из файла → поток пикселей с VGA-таймингами → параметризуемая оконная обработка (от 1×1 до 11×11) → фильтрация в Q-формате → запись результата обратно в файл.

---

## Что уже есть

### RTL

rtl/src/pixel_stream.sv — обвязка вокруг обработчика. Принимает поток пикселей активной области кадра вместе с h_sync_i / v_sync_i, формирует счётчики h_cnt / v_cnt и разворачивает входной кадр в поток с рамкой-дублем по краям (padding). Поддерживает произвольный нечётный размер окна WINDOW_W × WINDOW_H через параметры; строка хранится в кольцевом буфере lb размера V_DEL_WIDTH+1, из которого читается с нужной задержкой. Именно этот модуль готовит вход для оконного обработчика так, чтобы окно WINDOW_W × WINDOW_H всегда было полностью заполнено, включая края изображения.

rtl/src/proc_img.sv — оконный обработчик. Внутри:

- параметризация по WINDOW_W / WINDOW_H (поддерживаются оба варианта: WINDOW_H == 1 через отдельную generate-ветку, и WINDOW_H > 1 через набор строчных буферов);
- LINE_BUF_AMOUNT = WINDOW_H − 1 строчных буферов lb_mem (текущая строка не сохраняется — она и так есть в потоке);
- сдвиговый регистр окна wsr[WINDOW_H][WINDOW_W], обновляемый циклом for (без срезов нулевой ширины — работает и для 1×1);
- два такта конвейера для выравнивания pixel_i_wr / valid_i_wr / do_proc_pixel_wr относительно записи в lb_mem;
- инстанс weighted_sum_3x3 для взвешенной суммы с параметрами COEFF_N / COEFF_D;
- COEFF_N / COEFF_D вычисляются функцией make_center_coeffs() на уровне модуля (а не внутри generate) — это позволяет корректно инстанцировать фильтр для N_ELEMS == 1 и N_ELEMS > 1 без «Implicit COEFF_N»;
- generate-проверки WINDOW_W ≤ FRAME_W и WINDOW_H ≤ FRAME_H с $error на этапе elaboration.

rtl/src/weighted_sum_3x3.sv — обобщённый фильтр с фиксированной точкой. Модуль-обёртка weighted_sum_3x3 разбивает пиксель на каналы R/G/B и инстанцирует три одинаковых одноканальных фильтра weighted_sum_3x3_1ch. Внутри каждого:

- параметры Q_WIDTH / FRAC_PART задают Q-формат коэффициентов;
- COEFF_N / COEFF_D — массивы «числителей» и «знаменателей», по одному на элемент окна; функция init_coeffs() переводит их в Q-формат с округлением;
- конвейер из пяти стадий: mul → sum → round → shift → saturate, на каждой стадии — свой do_proc_pixel_*;
- насыщение результата в 0..255 с учётом знака.

Этот модуль заменяет собой box_blur3x3 там, где нужен не только box blur, но и произвольные коэффициенты (identity, sharpen, градиенты и т.д.).

rtl/src/box_blur3x3.sv — частный случай: box blur 3×3, собранный вручную (три одноканальных box_blur3x3_1ch с константой 1/9 в Q-формате). Оставлен как справочный/более компактный вариант для 3×3.

rtl/src/inverse_filter.sv — простая поэлементная инверсия 255 − x по каждому каналу, читающая центральный пиксель окна wsr[WINDOW_H/2][WINDOW_W/2]. Используется как эталон при отладке weighted_sum_3x3 с коэффициентами N=1, D=1.

### Тестбенч

tb/tb_top.sv — самодостаточный тестбенч:

- генерирует VGA-совместимые тайминги 640×480 @ 60 Hz (H: 640/16/96/48, V: 480/10/2/33);
- читает сырой RGB-поток из images/*.raw;
- подаёт пиксели в DUT ровно в те такты, когда активна область кадра;
- пишет результат в отдельный .raw файл по сигналу valid_o;
- считает и печатает статистику: pixels read / pixels written / expected — это позволяет ловить расхождения (например, «лишние» valid_o из-за залипания do_proc_pixel_pr во время гашения).

### Python-утилиты

python/img2raw.py — конвертирует PNG/JPG в плоский RGB-поток (3 байта на пиксель, row-major, сверху вниз, слева направо).

python/raw2img.py — обратная операция. Принимает .raw и путь для .png (по умолчанию кладёт рядом с исходником). Предупреждает, если размер файла не совпал с 640×480×3.

python/invert_raw.py — делает эталонный инвертированный .raw из исходного. Нужен для проверки, что DUT выдал именно то, что должен.

python/compare.py — побайтово сравнивает два .raw. Показывает количество несовпадающих байт, максимальное отклонение и индекс первого расхождения (с указанием пикселя и канала).

## Как это работает end-to-end

1. Изображение кладётся в images/, например lemme_chex.png.
2. img2raw.py превращает его в lemme_chex.raw.
3. tb_top.sv подаёт его потоком в pixel_stream с VGA-таймингами.
4. pixel_stream формирует паддинг по краям (через кольцевой lb) и отдаёт в proc_img непрерывный поток пикселей размером (H_ACTIVE_PIX + WINDOW_W − 1) × (V_ACTIVE_LINES + WINDOW_H − 1).
5. proc_img в каждом такте держит актуальное окно WINDOW_W × WINDOW_H и передаёт его в weighted_sum_3x3.
6. weighted_sum_3x3 считает Q-форматную взвешенную сумму и насыщает результат в 0..255.
7. Результат по valid_o пишется в lemme_chex_inv.raw.
8. raw2img.py показывает картинку, compare_inv.py — говорит, всё ли точно.

## Архитектурные заметки

### Паддинг и параметризация окна

Краевые пиксели дублируются, чтобы окно WINDOW_W × WINDOW_H не выходило за пределы изображения. Логика реализована в pixel_stream через кольцевой буфер lb[0:V_DEL_WIDTH][0:H_ACTIVE_PIX-1] и счётчики lb_line_rd/wr, lb_head_rd/wr. Размер lb — V_DEL_WIDTH + 1 строк, где V_DEL_WIDTH = WINDOW_H / 2. На выходе proc_img отдаёт ровно H_ACTIVE_PIX × V_ACTIVE_LINES валидных пикселей; «лишние» (расширенный кадр) уходят в паддинг.

### Fixed-point арифметика

Реализована в weighted_sum_3x3. Формат знаковый: Q_WIDTH бит всего, FRAC_PART дробных, целая часть (со знаком) = Q_WIDTH − FRAC_PART − 1.

Основные ограничения на параметры Q-формата:

- FRAC_PART ≥ 8 + ceil(log2(N_ELEMS)) — иначе после суммирования N_ELEMS членов теряется младший бит 8-битного пикселя (нарушается «сохранение цвета»). Для окна 13×13 (N_ELEMS = 169) нужно FRAC_PART ≥ 16, поэтому при FRAC_PART = 15 окно 13×13 даёт расхождение в 1 LSB, а 11×11 (N_ELEMS = 121) — ещё укладывается.
- FRAC_PART ≤ Q_WIDTH − 1 — иначе дробная часть не помещается в знаковый формат.
- Q_WIDTH − FRAC_PART − 1 ≥ ceil(log2(max |N_k / D_k|)) — целая часть должна вмещать максимальный коэффициент.
- Для Σ|N_k/D_k| ≤ 1 гарантируется отсутствие насыщения на «обычных» изображениях (для сглаживающих фильтров с нормировкой это выполнено).

При Q_WIDTH = 20 и FRAC_PART = 15: int_bits = 4, дроби 1/9, 1/25, 1/169 представимы, но FRAC_PART = 15 покрывает N_ELEMS только до 128.

### Тайминговые ограничения

pixel_stream жёстко связан с таймингами h_sync_i / v_sync_i. Последний valid_o должен успеть выйти до фронта h_sync_i, иначе хвост строки отрезается. При суммарной задержке конвейера PIPELINE_DELAY_H ≈ 6 тактов (2 в proc_img + 4 в weighted_sum_3x3) должно выполняться:

    WINDOW_W + PIPELINE_DELAY_H ≤ H_FRONT_PORCH_PIX + 1

При стандартных VGA-таймингах (H_FRONT_PORCH_PIX = 16) это даёт WINDOW_W ≤ 11. Для WINDOW_W = 13 нужно увеличивать H_FRONT_PORCH_PIX / H_SYNC_PIX или уменьшать конвейер. Аналогичное ограничение по вертикали через V_DEL_WIDTH и V_FRONT_PORCH_LINES.

### Generate-проверки параметров

В модулях добавлены elaboration-time проверки через generate + $error / $warning:

- pixel_stream: нечётность и положительность WINDOW_W / WINDOW_H, влезание в H_ACTIVE_PIX / V_ACTIVE_LINES, тайминговые ограничения, разрядность счётчиков h_cnt / v_cnt.
- proc_img: WINDOW_W ≤ FRAME_W, WINDOW_H ≤ FRAME_H, FRAME_W ≥ 2 для $clog2, предупреждение при чётном окне.
- weighted_sum_3x3: Q_WIDTH ≥ 2, 1 ≤ FRAC_PART ≤ Q_WIDTH − 1, FRAC_PART ≥ 8 + clog2(N_ELEMS), проверка что каждый коэффициент N_k/D_k влезает в целую часть Q-формата, COEFF_D[k] ≠ 0 для всех k.

Все проверки работают на этапе elaboration и не создают логики. Они защищают от типовых ошибок вроде срезов нулевой ширины, залипания do_proc_pixel_pr и переполнения разрядности.

## Roadmap

- **Совместная работа нескольких фильтров.** Сейчас weighted_sum_3x3 — единственный фильтр в pipeline. Хочется уметь ставить несколько последовательно (blur → sharpen → threshold) с корректным протаскиванием valid между стадиями.

### Средний план

- **VGA-вывод.** Логика таймингов уже реализована в тестбенче, её нужно вынести в отдельный RTL-модуль и подать на физический ЦАП (R-2R) или на VGA-разъём через резисторную сборку. Это позволит видеть результат обработки в реальном времени на мониторе.
- **Интеграция в FPGA.** Выбрать плату (что-то из Cyclone / Artix / Lattice), развести clock domain, подключить PLL, написать топовый модуль с привязкой к пинам. Первая цель — прогнать weighted_sum_3x3 с разными коэффициентами на живом видео.
- **Ввод данных.** Разобраться с SPI (как основной кандидат для приёма кадров от внешнего источника) или с чтением из внешней SRAM/SDRAM. Пока не решено, какой протокол использовать.

## Структура репозитория

    rtl/
      headers/
        img_pkg.svh            — пакет с pixel_t и fract_t
      src/
        pixel_stream.sv        — VGA-тайминги + паддинг + обвязка обработчика (параметризуемое окно)
        proc_img.sv            — оконный обработчик WINDOW_W × WINDOW_H + строчные буферы
        weighted_sum_3x3.sv    — Q-форматная взвешенная сумма (обёртка + 1ch)
        box_blur3x3.sv         — box blur 3×3 как частный случай (справочно)
        inverse_filter.sv      — поэлементная инверсия (эталон)
    tb/
      tb_top.sv                — тестбенч с VGA-генератором, файловым I/O и счётчиками пикселей
    python/
      img2raw.py               — PNG/JPG -> raw RGB
      raw2img.py               — raw RGB -> PNG
      invert_raw.py            — эталонная инверсия raw
      compare.py               — побайтовое сравнение
    images/
      lemme_chex.png           — исходник
      lemme_chex_inv.raw       — выход DUT
    build/
      wave.vcd                 — дамп сигналов

## Что пока не сделано

- Нет RTL-модуля для VGA-вывода (тайминги есть только в TB).
- Нет синтезируемого топового модуля и constraint-файла.
- Нет интерфейса ввода данных с внешнего источника.
- Параметризация окна протестирована для 1×1, 3×3, 5×5, 11×11; для 13×13 и выше упирается в тайминговое ограничение (см. «Архитектурные заметки»).

Это учебный проект, поэтому структура и API модулей могут меняться по мере освоения новых тем.
